# ADR-0019: Deploy remote sessions with explicit cloud workspace providers

**Status**: Accepted / implemented through PR #121
**Date**: 2026-05-05

## Context

ADR-0013 and ADR-0015 define PostgreSQL-backed HTTP sessions as owner-routed,
lease-bound, and at-most-once for in-flight turns. ADR-0017 adds the
provider-neutral `CloudEnvironment` and `CloudWorkspaceClient` boundary. ADR-0018
accepts owner-local, cloud-aware subagent orchestration: child agents inherit the
parent environment and remain an implementation detail of the current parent
session owner.

Those decisions make the local/cloud runtime contract executable, but the
deployable product shape is still incomplete. `CloudWorkspaceBinding` can be
stored on a session, yet the default HTTP server does not construct a real cloud
client factory from configuration. A cloud-bound session therefore fails fast
unless tests inject a fake factory. The CLI and REPL still assume local runtime
ownership, and `serve` exposes HTTP session APIs but not a first-class local
client workflow for attaching to a remote session manager.

External agent systems point at the same boundary. YA Claw separates workspace
providers, workspace bindings, environment factories, and runtime builders.
Codex uses an app-server/worker shape where clients drive a long-lived runtime
near the workspace. OpenCode's serve/attach issues show why a workspace id is not
enough unless tool execution also uses that workspace as the effective cwd.
Claude Code Remote Control keeps the UI remote while tools execute where the
workspace lives. This repository should adopt the same principle: the user
interface may be local, but file and shell tools must execute in the workspace
bound to the remote session.

## Decision

Implement the deployable remote shape as three explicit roles:

1. **Local client**
   - Owns TUI/CLI rendering, prompt submission, approval responses, and remote
     connection metadata.
   - May upload an initial workspace snapshot or request a server-side workspace
     source.
   - Does not execute agent tools for cloud-bound sessions.
2. **Remote session manager**
   - Runs `coding_agent serve` as the control plane.
   - Owns active runtime state, SSE delivery, approval routing, checkpoint
     operations, and owner lease renewal.
   - Requires PostgreSQL-backed HTTP session metadata, tape storage, checkpoint
     storage, and owner records for multi-instance deployments.
3. **Cloud workspace executor**
   - Implements `CloudWorkspaceClient` for a concrete remote workspace backend.
   - Supplies file, patch, grep/glob, and shell execution to `CloudEnvironment`.
   - Runs tools in the bound workspace path and never falls back to local
     filesystem or local shell execution.

The implementation should add a `WorkspaceProvider` layer in `coding_agent`, not
`agentkit`. The provider returns a declarative workspace binding for a session;
a cloud client factory turns that binding into a `CloudWorkspaceClient`; the
existing `DefaultBindingResolver` turns the client into `CloudEnvironment`.
Provider-specific credentials, container lifecycle, workspace upload/sync, and
path policy stay in `coding_agent`.

The first concrete provider should be a Docker-backed cloud workspace provider:

- The remote service stores workspace data under a configured server-side root,
  for example `/srv/coding-agent/workspaces/<workspace_id>`.
- The Docker container exposes that workspace as `/workspace` and uses
  `/workspace` as `default_cwd`.
- File operations read and write the server-side workspace tree through the
  provider client.
- Shell execution runs through `docker exec` with cwd, env, timeout, and user
  identity derived from provider configuration.
- Environment variables are passed only from an explicit allowlist.
- Workspace ids and trace metadata are generated by the server, not trusted from
  clients.

Remote session creation must resolve workspace intent before runtime creation.
The HTTP API should accept either an existing `execution_binding` or a workspace
source request. A workspace source request may be a local-client upload bundle,
a server-side path/worktree source, or a provider-native workspace id. The server
then stores the resulting `CloudWorkspaceBinding` on session metadata. Existing
cloud bindings remain supported for tests and trusted integrations, but a
production server with cloud workspaces enabled must construct a cloud client
factory at startup.

The first local client workflow should be attach-oriented:

- `coding-agent remote add/list/remove` manages named remote endpoints and bearer
  tokens in user-local config.
- `coding-agent remote repl <name> --repo <path>` creates a remote session,
  uploads a workspace snapshot or selects a configured source, streams events,
  and submits approvals.
- `coding-agent attach <name> --session <session_id>` reconnects to an existing
  remote session and resumes event/approval control.
- Sessions record optional origin metadata so users can distinguish local,
  remote, Docker, and future provider-backed sessions.

The first workspace transfer contract should be explicit snapshot upload plus
explicit result download or patch export. Bidirectional live sync is deferred.
Live sync has conflict, rename, ignore-rule, and trust-policy complexity that is
not needed to prove remote execution. A later ADR must define any watch-based or
bidirectional sync protocol.

The owner-local subagent invariant from ADR-0018 remains unchanged. A child agent
inherits the parent `CloudEnvironment` and the same `CloudWorkspaceClient`
instance. Child agents still run inside the parent session owner process and use
the existing owner-local `ChildWorkerCoordinator` write lease. This ADR does not
allow distributed child workers.

## Implementation Plan

### PR 1: Cloud provider factory and server wiring

- Add `coding_agent.environment.workspace_provider` or equivalent app-layer
  module with `WorkspaceProvider`, provider config parsing, and a
  `CloudWorkspaceClientFactory`.
- Extend `_build_session_manager()` so `agent.toml` `[cloud_workspace]` settings
  can construct `DefaultBindingResolver(cloud_client_factory=...)`.
- Keep missing or disabled cloud provider config fail-fast for cloud bindings;
  do not fall back to local bindings.

### PR 2: Docker cloud workspace provider

- Implement `DockerCloudWorkspaceClient` in `coding_agent`.
- Support file read/write/replace, grep/glob, patch, and shell execution with
  cwd/env/timeout.
- Add path policy proving `/workspace` is the only model-facing workspace root.
- Add deterministic timeout and process cleanup behavior for shell commands.

### PR 3: Remote session creation and attach client

- Add request schemas for workspace source creation.
- Add HTTP session creation support that provisions a cloud workspace before
  persisting the session.
- Add `remote` and `attach` CLI surfaces that submit prompts, stream SSE events,
  and submit approval responses against a named remote endpoint.
- Persist session origin metadata for remote sessions.

### PR 4: Workspace transfer and operational hardening

- Add explicit workspace snapshot upload and result download/patch export.
- Add readiness checks for configured cloud workspace providers.
- Document production deployment with PostgreSQL session/tape/checkpoint storage,
  owner lease configuration, bearer-token authentication, TLS or private-network
  transport, and Docker workspace isolation.

## Implementation Status

Implemented on `main` through PR #121:

- `coding_agent.environment.workspace_provider` defines the provider boundary for
  cloud client factories, workspace provisioning/cleanup, readiness checks, and
  workspace archive import/export.
- `DockerWorkspaceProvider` is the first concrete provider. It provisions a
  server-side workspace directory plus a Docker container, maps that directory
  into the configured container workspace root, executes commands with
  `docker exec`, and removes the container/workspace during cleanup.
- The HTTP server can create sessions from a `workspace_source`, persist cloud
  origin metadata, resolve provisioned cloud sessions into `CloudEnvironment`,
  export workspace archives, and report cloud workspace readiness from `/readyz`.
- The remote CLI supports `remote add/list/remove`, `remote repl` with either a
  local workspace snapshot or an explicitly empty workspace, and `attach` for
  submitting prompts to an existing remote session.
- Workspace transfer uses bounded `tar.gz` archives encoded as base64. Archive
  extraction rejects path traversal, symlinks, preserved root entries such as
  `.git`, excessive decoded/compressed size, excessive decompressed stream size,
  and excessive member count before replacing the local workspace contents.
- Docker workspace containers are hardened by default with no network,
  capability drop, `no-new-privileges`, PID/CPU/memory limits, and image
  allowlist enforcement. When `exec_user` is configured, the same user is
  applied to both the provisioned container and subsequent `docker exec` calls.

Still out of scope for this ADR implementation:

- Bidirectional live sync.
- Distributed child workers.
- Non-Docker cloud workspace providers such as SSH, Kubernetes, or microVMs.

## Alternatives Rejected

- Treat `workspace_url` as enough and leave tool cwd unchanged — rejected because
  OpenCode-style workspace id/session directory drift lets tools run in the wrong
  workspace while metadata claims otherwise.
- Execute cloud-bound tools on the local client and stream results to the remote
  session — rejected because it splits approval, cwd, filesystem, and process
  authority across machines and bypasses session owner fencing.
- Add bidirectional live sync in the first cut — rejected because conflict
  resolution, ignore handling, and rename semantics are a separate protocol.
- Put Docker or provider clients in `agentkit` — rejected because credentials,
  workspace lifecycle, container policy, and deployment configuration are
  `coding_agent` product concerns.
- Add distributed child workers now — rejected because ADR-0018 explicitly keeps
  child agents owner-local until a future ADR defines distributed coordination,
  fencing, retry, and cloud workspace write policy.
- Use Redis-only session metadata for remote session management — rejected for
  multi-instance remote execution because owner leases, fencing tokens, tape
  history, and checkpoints need one durable coordination substrate. Redis may
  remain a cache/rate-limit backend, not the first remote execution authority.
